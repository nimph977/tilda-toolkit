# Рабочий цикл

Инвариант: **снимок до записи, сверка после**. Любая запись проходит одним запуском
`apply`: инвентарь → снимки затронутых блоков → подготовка → запись → перечитать → `verify`.

## Обычный цикл

0. Если вы не знаете `pageid` нужной страницы, получите перечень страниц проекта. Итог
   покажет первые пять страниц, полный список ляжет в `<папка сайта>/site-baseline/pages/<projectid>.json`:

   ```powershell
   node scripts/tilda.mjs --site <папка сайта> page list
   ```

1. Откройте браузер-держатель и войдите в Tilda:

   ```powershell
   node scripts/tilda.mjs --site <папка сайта> session --page 200002
   ```

2. Снимите текущее состояние страницы до правки:

   ```powershell
   node scripts/tilda.mjs --site <папка сайта> snapshot --page 200002
   ```

3. Создайте план операций (JSON). Схема и безопасный синтетический пример — в
   [skills/tilda-manager/references/plan-schema.md](../../skills/tilda-manager/references/plan-schema.md) и
   [examples/basic-text-edit.json](../../examples/basic-text-edit.json). Не копируйте пример
   в рабочий план без замены всех ID.

4. Посмотрите, что будет изменено, без записи:

   ```powershell
   node scripts/tilda.mjs --site <папка сайта> preview --page 200002 --plan .\my-plan.json
   ```

5. Примените план и проверьте результат:

   ```powershell
   node scripts/tilda.mjs --site <папка сайта> apply --page 200002 --plan .\my-plan.json
   node scripts/tilda.mjs --site <папка сайта> verify --page 200002 --plan .\my-plan.json
   ```

   Ожидаемый итог: `расхождений verify: 0`, код выхода 0. При расхождениях код выхода 1 —
   не публикуйте, изучите журнал или откатите запись.

6. Откройте страницу в редакторе и проверьте визуально на нужных ширинах
   (`shot --width 1440,320` снимает скриншоты вида). Публикация выполняется отдельной
   явной командой только после этой проверки:

   ```powershell
   node scripts/tilda.mjs --site <папка сайта> page publish --page 200002 --confirm
   ```

## Откат

Снимок — локальная фиксация состояния для сверки и подготовки отката. Он не равен
экспорту Tilda и не восстанавливает проект целиком. Для отката используйте запись
журнала, созданную успешным `apply`:

```powershell
node scripts/tilda.mjs --site <папка сайта> journal --page 200002
node scripts/tilda.mjs --site <папка сайта> rollback "<папка сайта>\site-baseline\journal\200002\<record>.json"
```

Откат — тот же цикл с обратным планом и той же сверкой; он тоже пишет запись в журнал.

## Массовая замена текста

По локальным снимкам, без браузера:

```powershell
node scripts/tilda.mjs --site <папка сайта> find "старый текст" --page 200002
node scripts/tilda.mjs --site <папка сайта> replace "старый текст" "новый текст" --page 200002
node scripts/tilda.mjs --site <папка сайта> apply --plan "<папка сайта>\plans\replace-200002.json"
```

Поля форм при поиске и замене пропускаются.

## Накат с копии на живую страницу (`promote`)

Порядок: план проверен на копии по журналу → бэкап-дубль живой страницы и полный снимок →
сверка бэкапа с копией (расхождение сверх плана — останов) → накат → бэкап остаётся.

```powershell
node scripts/tilda.mjs --site <папка сайта> promote --plan .\my-plan.json --from 200002 --to 200001 --unprotect
```

Защита живой страницы снимается только флагом `--unprotect` на этот вызов.

## Сборка страницы по референсу

Референс — опубликованный сайт (свой или тот, на который вы имеете право опираться);
кабинет его владельца не нужен. Страница собирается в вашем проекте из стандартных блоков
Tilda: тексты, ссылки кнопок, карточки списков и картинки берутся из опубликованного HTML,
а имена полей редактора — из каталога, снятого с эталонных блоков на черновой странице.

Все команды — из корня репозитория (или по пути к нему) с `--site <папка сайта>`. Для шагов 2–8 нужна папка
сайта с `.env`, где задан `TILDA_PROJECT_ID` тестового проекта, `TILDA_PROTECTED_PAGES=` (пустой список)
и `TILDA_CATALOG_DIR`; черновая страница создаётся в этом проекте.

```powershell
# 1. Слепок референса: HTML главной, структура блоков, картинки -> <папка сайта>/site-reference/demo/
node scripts/tilda.mjs --site <папка сайта> reference fetch --url https://ref.test/ --slug demo --images
# 2. Вход в Tilda в окне держателя (окно развернётся до входа, затем свернётся)
node scripts/tilda.mjs --site <папка сайта> session --wait 600
# 3. Черновая страница в тестовом проекте -> запомните pageid из ответа
#    (забыли — page list покажет все страницы проекта)
node scripts/tilda.mjs --site <папка сайта> page create
# 4. Каталог полей: по одному блоку каждого шаблона из слепка создать, прочитать, удалить
node scripts/tilda.mjs --site <папка сайта> catalog capture --page 200002 --slug demo
# 5. План сборки: операции newRecord по структуре и каталогу -> <папка сайта>/plans/reference-demo-index-200002.json
#    по умолчанию переносит отступы, фон и типографику; --no-styles отключает
node scripts/tilda.mjs --site <папка сайта> reference plan --slug demo --source index --page 200002
# 6. Проверка без записи: список блоков и предупреждения о полях
node scripts/tilda.mjs --site <папка сайта> apply --plan <папка сайта>/plans/reference-demo-index-200002.json --dry-run
# 7. Сборка: картинки на CDN -> блоки -> перечитать -> verify без расхождений
node scripts/tilda.mjs --site <папка сайта> apply --plan <папка сайта>/plans/reference-demo-index-200002.json
# 8. Скриншоты для приёмки на 1440 и 320 -> <папка сайта>/site-baseline/shots/200002/
node scripts/tilda.mjs --site <папка сайта> shot --page 200002 --width 1440,320
```

### Меню, которое Tilda не даёт добавить

Шаблоны меню часто помечены `available: false` в каталоге (`You do not have access to this
block`) — их нельзя создать ни одной командой. По справке Tilda это, вероятно, архивные блоки:
на опубликованных сайтах они работают, но добавить новый нельзя. Обход — собрать такой блок
другим шаблоном меню, который проект добавить даёт. Замена выглядит по-своему: например, шапка
на `3535` вместо `770` теряет верхнюю строку со слоганом и часть оформления.

```powershell
# 4а. Владелец добавляет в редакторе черновой страницы любой блок из раздела «Меню»
node scripts/tilda.mjs --site <папка сайта> inventory --page 200002   # tplid нового блока в _inventory.json
node scripts/tilda.mjs --site <папка сайта> catalog capture --page 200002 --tplid 3535
# затем блок из редактора удалить: каталог снят, эталон больше не нужен
node scripts/tilda.mjs --site <папка сайта> reference plan --slug demo --source index --page 200002 --substitute 770=3535
```

Пункты меню переносятся в поле `menuitems` шаблона-замены, а если он хранит список — карточками
`li_title`/`li_link`. Замена работает только по явному флагу: таблиц соответствия шаблонов в
инструменте нет. Адреса пунктов переносятся как у референса — правьте их после того, как собраны
все страницы.

### Пропуски и несопоставленные поля

Итог `reference plan` перечисляет `skipped` (блоки, которые не собираются) и `unmapped`
(поля, которые не перенеслись); в итоге выводятся первые 20 записей каждого списка, число
несопоставленных полей — в `unmappedTotal`. Их дорабатывают вручную операциями `field`/`stage`
или в интерфейсе Tilda. Ожидаемые пропуски: Zero Block, HTML-блоки, блоки-формы, шаблоны,
которые Tilda не даёт добавить (`template is unavailable on the plan — pass --substitute
<tplid>=<available one>`), пустые разделители.

Причина всегда говорит, что именно осталось невыполненным. В плане у каждой причины два поля:
`reason` — текст на английском и `code` — машинный код. Они не зависят от языка запуска
(`--lang`), поэтому таблицы ниже дают оба:

| `code` и `reason` | Что значит |
| --- | --- |
| `spacing` — `spacing: the margintop/marginbottom fields are not in the catalog` | у шаблона нет полей отступов — расстояние останется шаблонным |
| `background` — `background: there is no background field in the catalog` | шаблон не хранит цвет фона блока |
| `typography` — `typography: the <family>_typo field is not in the catalog` | у шаблона нет такого семейства текста |
| `soclinksNoField` — `social links: there is no soclinks field in the catalog` | иконки соцсетей некуда записать |
| `soclinksShape` — `social links: the soclinks format of the template is not supported` | блок мессенджеров (форма `type`/`username`) |
| `cardNoLink` — `card link: the template does not store li_link` | карточки списка не кликабельны у этого шаблона |
| `menuNoTarget` — `menu: the template has no menuitems or li_title/li_link list` | шаблон-замена не годится для меню |
| `substituteCatalogMissing` — `substitute catalog not captured: catalog capture --tplid <id>` | снимите каталог шаблона-замены, затем повторите `reference plan` |

Что переносится: тексты с переносами строк, ссылки кнопок и карточек (`li_link`), картинки,
карточки списков, иконки соцсетей, пункты меню, отступы блока, цвет фона и типографика
(цвет, кегель, начертание, капитель, межстрочное, ширина колонки).

Что не переносится без строгой копии (см. следующий раздел): настройки блоков сверх отступов,
фона и типографики — цвета кнопок, число колонок, высоты; поля форм, код HTML-блоков,
мессенджеры 898, шрифты проекта. Не переносятся никогда: Zero Block, недоступные шаблоны без
явной замены. Шапку и подвал назначает `page role`. Поля, которых у референса не было,
обнуляются, чтобы на странице не остались демо-значения шаблона Tilda, — проверьте их на
скриншотах.

Если сборка оборвалась: журнал `<папка сайта>/site-baseline/reread/<pageid>/_built.json` показывает, какие
блоки созданы (`status: ok`) и на каком остановились. Повтор того же плана создаст дубли —
сначала удалите созданные блоки в редакторе (или урежьте план до несобранных операций и
укажите `startAfter` = `recordid` последнего собранного блока). `catalog capture` и
`reference fetch` возобновляются сами: снятое пропускается.

Публикация — отдельное действие (`page publish --page <id> --confirm`) после ручной приёмки.

## Строгая копия

Строгая копия переносит сверх текстов и картинок то, что задано настройками блоков и проекта:
число колонок, высоты, прозрачности, цвета и скругления кнопок, анимации, кнопки карточек,
поля форм (без получателей), мессенджеры 898, код HTML-блоков, шрифты и цвета проекта.
Настройки восстанавливаются по разметке референса через **карту влияния**: для каждого шаблона
предпросмотром Tilda снимается, как каждое значение настройки меняет разметку блока, а затем
признаки блока референса разбираются по этой карте.

**Честный вывод.** Строгая копия без кабинета владельца референса возможна, но долгая и
требует ручной доработки. Калибровка 40 шаблонов идёт около 5,5 часа, большая часть времени —
паузы темпа. После сборки остаются отличия, которые видны только на снимках:
- настройки без следа в разметке не восстанавливаются;
- одинаковый признак у разных элементов блока путает разбор (например, `height:560px`
  у картинки и у линии в `480`);
- архивные шаблоны заменяются шаблоном со своим видом.

Приёмка — поблочное сравнение снимков сборки и референса в полном размере на 1440 и 320, а не
просмотр уменьшенного снимка страницы. Перенос через кабинет владельца референса — раздел
«Перенос через кабинет донора» ниже.

```powershell
# 1. Структура с признаками разметки (без сети)
node scripts/tilda.mjs --site <папка сайта> reference structure --slug demo
# 2. Карты влияния для шаблонов слепка — после «делай» владельца: создаёт и удаляет временные
#    блоки на черновой; повтор той же команды пропускает откалиброванное
node scripts/tilda.mjs --site <папка сайта> catalog calibrate --page 200002 --slug demo
node scripts/tilda.mjs --site <папка сайта> catalog list          # колонка calibrated
# 3. Оформление проекта: сначала посмотреть, запись — после «делай» (меняет вид всех страниц)
node scripts/tilda.mjs --site <папка сайта> reference project --slug demo
node scripts/tilda.mjs --site <папка сайта> reference project --slug demo --apply --confirm
# 4. Новая страница — план по метке; уже собранная — дописывание без пересоздания блоков
node scripts/tilda.mjs --site <папка сайта> reference plan --slug demo --source P00 --update
node scripts/tilda.mjs --site <папка сайта> apply --plan <папка сайта>/plans/reference-demo-P00-update.json --dry-run
node scripts/tilda.mjs --site <папка сайта> apply --plan <папка сайта>/plans/reference-demo-P00-update.json
# 5. Сверка разметки по блокам и ссылок
node scripts/tilda.mjs --site <папка сайта> reference compare --slug demo --source P00
node scripts/tilda.mjs --site <папка сайта> reference audit --slug demo --source P00
# 6. Снимки для приёмки тем же инструментом на тех же ширинах
node scripts/tilda.mjs --site <папка сайта> shot --page 200003 --width 1440,320
node scripts/tilda.mjs --site <папка сайта> reference shot --slug demo --source P00 --width 1440,320
```

Гейты владельца: «делай» перед калибровкой и перед записью оформления проекта; приёмка по
снимкам 1440 и 320; публикация — только отдельным действием с подтверждением.

### Что не переносится и почему

Причины в плане (`code` и английский `reason`, не зависят от языка запуска):

| `code` и `reason` | Что значит |
| --- | --- |
| `formReceivers` — `form: request recipients are a setting of the copy project, not transferred` | куда уходят заявки, задаёт владелец копии |
| `formInputUnknown` — `form: field type <type> is not recognized` | поле формы с незнакомым типом пропущено |
| `codeScriptsRemoved` — `HTML block: scripts are removed — writing them resets the Tilda session` | `<script>` в коде HTML-блока не пишется |
| `codeTooLarge` — `HTML block: the code is larger than 25 KB` | большой код переносится вручную |
| `settingsSubstituted` — `settings: template <a> is replaced by <b> — only spacing, background and typography are transferred` | архивный шаблон собран заменой со своим видом |
| `settingsNoMap` — `settings: the template is not calibrated — catalog calibrate` | для шаблона нет карты влияния |
| `settingsUndecided` — `settings: the value is not recognized by the map (<why>)` | признак подходит под несколько значений (`ambiguous`) или не найден (`absent`) |
| `settingsUnexplained` — `settings: markup features without a field — the number is in text` | в разметке есть признаки, которые не объясняет ни одна настройка — например, другая версия шаблона у референса |
| `updatePlacement` — `the new block will be placed after the previous new one — move it after block <id>` | дописывание: блок создан не на своём месте |
| `updateImageKept` — `the image is already on the page — it is not uploaded again` | дописывание картинки не трогает |

Тексты итога и докладов пишутся на языке запуска (здесь — русский вариант):

| Причина в итоге или докладе | Что значит |
| --- | --- |
| `свои шрифты не переносятся — выбран пресет Tilda с тем же начертанием` | шрифт проекта заменяется пресетом Tilda (итог `reference project`) |
| `разметка отличается — возможно, версия шаблона` | доклад сверки: блок референса сделан другой версией шаблона |

Не разведаны: Zero Block и настройки, которые не меняют разметку (`noSignal` в карте) — их
значения по разметке не восстановить.

## Перенос через кабинет донора

Донор — аккаунт Tilda с сайтом-образцом, к кабинету которого у владельца есть доступ. Если
аккаунт донора добавлен сотрудником в тестовый проект, под его входом видны оба проекта.
Тогда блоки страницы донора, включая архивные, которые Tilda не даёт добавить из библиотеки,
копируются в буфер аккаунта и вставляются на страницу тестового проекта запросами редактора.
Страница переносится байт в байт, без калибровки и ручной доработки.

Выбирайте этот путь, когда доступ к кабинету донора есть. Без доступа остаётся сборка по
опубликованному сайту (разделы выше).

Проект донора не меняется: команды только читают его и копируют блоки в буфер. Сессия донора
пишет только в одну разрешённую страницу-приёмник на время вставки. Любая другая запись
отказывает `WRITE_NOT_ALLOWED` ещё в браузере. После копирования и после вставки команда
сверяет состав страницы донора с исходным.

```powershell
# 0. Предпосылки: аккаунт донора — сотрудник тестового проекта (делает владелец);
#    в .env папки сайта заданы TILDA_DONOR_PROJECT_ID и TILDA_DONOR_BROWSER_PROFILE;
#    есть слепок demo и карта сайта (reference fetch, reference pages --create)
# 1. Держатель донора и вход: окно на экране только до входа человека
node scripts/tilda.mjs --site <папка сайта> browser start --donor
node scripts/tilda.mjs --site <папка сайта> session --donor
# 2. Перечень страниц донора и карта меток (donorPageid в site.json)
node scripts/tilda.mjs --site <папка сайта> donor pages
node scripts/tilda.mjs --site <папка сайта> donor map --slug demo
# 3. Оформление и шрифт донора: прочитать, запись — после «делай» (меняет вид всех страниц)
node scripts/tilda.mjs --site <папка сайта> donor style --slug demo
node scripts/tilda.mjs --site <папка сайта> donor style --slug demo --apply --confirm
# 4. Перенос страницы: сначала план, запись под входом донора — после «делай»
node scripts/tilda.mjs --site <папка сайта> donor copy --slug demo --source HDR --dry-run
node scripts/tilda.mjs --site <папка сайта> donor copy --slug demo --source HDR --replace
# 5. Сверка: состав, разметка, кадры 1440 и 320, доклад reports/P00.transfer.md
node scripts/tilda.mjs --site <папка сайта> donor verify --slug demo --source P00
# 6. Шапка и подвал проекта — после «делай»
node scripts/tilda.mjs --site <папка сайта> page role --header 200002 --footer 200003 --confirm
# 7. Адреса страниц копии как у страниц донора: вход донора не нужен, запись в тестовый проект
node scripts/tilda.mjs --site <папка сайта> page list
node scripts/tilda.mjs --site <папка сайта> donor aliases --slug demo --dry-run
node scripts/tilda.mjs --site <папка сайта> donor aliases --slug demo
# 8. Ссылки донора → пути на страницы копии: HDR, FTR, затем метки, которые отмечает проверка
node scripts/tilda.mjs --site <папка сайта> donor links --slug demo --source HDR --dry-run
node scripts/tilda.mjs --site <папка сайта> donor links --slug demo --source HDR
# 9. Проверки после переноса по всем меткам: итог — раздел сводки reports/transfer-summary.md
node scripts/tilda.mjs --site <папка сайта> donor check --slug demo
# 10. Главная не та — страница метки главной донора (команду подсказывает donor check), затем повтор
node scripts/tilda.mjs --site <папка сайта> page role --index 200001 --confirm
node scripts/tilda.mjs --site <папка сайта> page list
node scripts/tilda.mjs --site <папка сайта> donor check --slug demo
```

Шаги 4 и 5 повторяются для каждой метки по одной, с паузой не меньше 3 секунд. Сначала
переносите шапку `HDR` и подвал `FTR`: их видно на кадре каждой страницы. Перед пакетом
агент показывает владельцу метки, число блоков из `--dry-run` и приёмники, которые очистит
`--replace`; одно «делай» может покрывать весь пакет. Метка без `donorPageid` переносится
явно: `donor copy --from <pageid донора> --to <pageid>`.

Перед пакетом сверьте полноту карты: число страниц донора в `donor pages` против числа
уникальных `donorPageid` в `site.json`. Карта строится по опубликованному сайту, поэтому
страницы без входящих ссылок, например страница 404, в неё не попадают, и `donor map` об этом
молчит. Каждую такую страницу назовите владельцу, его решение запишите в сводку. Страницу 404
назначают в настройках тестового проекта вручную.

Блоки переносятся байт в байт, поэтому ссылки в них остаются донорскими. Относительные адреса
(`/company` в меню шапки) ведут на 404, пока у страниц копии нет тех же адресов. Абсолютные
ссылки на домен донора уводят посетителя на живой сайт донора. Шаг 7 даёт страницам копии адреса
их страниц донора. Шапка, подвал и главная пропускаются, адрес, занятый другой страницей
тестового проекта, не отбирается. `donor copy --source` ставит адрес приёмнику сам, если адреса
у него ещё нет. Шаг 8 переписывает ссылки донора в пути на страницы копии: адреса на домене
донора и ссылки на страницы донора по ID (`/page<ID донора>.html` — относительные, на домене
донора и на его поддомене `*.tilda.ws`) по парам карты сайта. План строится только по живым
блокам страницы: снимки блоков, удалённых `donor copy --replace`, пропускаются. Меняется
только адрес ссылки, видимый текст остаётся. Путь без страницы в копии остаётся ссылкой на донора,
команда называет его с причиной. Поле формы `formmsgurl` (переход после отправки) не меняется,
его нужно назвать владельцу. `donor links` снимает блоки до записи и сверяет их после (`verify`).
Если сверка расходится, восстанавливайте страницу через `donor copy --replace` и `donor aliases`,
не через `rollback`.

Кадры предпросмотра не показывают ни 404, ни уход на сайт донора, ни HTML-блоки. До приёмки
пройдите весь список «Проверки после переноса» из
[сценариев скилла](../../skills/tilda-manager/references/scenarios.md). Шаг 9 (`donor check`)
выполняет автоматические пункты по всем перенесённым меткам: ссылки вида страницы (домен донора,
относительные адреса без страницы, страницы донора по ID), HTML-блоки с заглушкой или внешними
хостами, `formmsgurl` на домене донора, полноту карты и главную страницу проекта. Итог — раздел
между маркерами `<!-- donor-check:start -->` и `<!-- donor-check:end -->` в
`reports/transfer-summary.md`; остальной текст сводки команда не трогает. Ручные пункты
(получатели заявок, страница 404, запрет индексации, отличия от публикации донора) перечислены
в том же разделе. Нарушений ссылок должно быть 0; HTML-блоки и формы назовите владельцу.
Если главная не та, раздел и строка `next` дают готовую команду шага 10 — `page role --index` со
страницей метки главной донора; агент выполняет её сам (запись в тестовый проект), затем
`page list` и повторный `donor check`: 0 нарушений и «главная назначена верно».

Приёмка: агент осматривает кадры сборки и референса и пишет раздел «Вердикт агента» в каждом
докладе, затем составляет сводку `reports/transfer-summary.md`. Повторный `donor verify`
переносит заполненный вердикт с пометкой о дате прежнего доклада — перепроверьте его по новым
кадрам. Владелец подтверждает вывод.
Откат неудачного переноса — повторный `donor copy --replace`, не `rollback`.

Гейты человека: доступ сотрудника и оплата, вход в аккаунт донора, каждый запуск
`donor copy` или пакет запусков, запись оформления, подтверждение приёмки, публикация.
Пошаговый сценарий для агента и журнал ручных шагов — скилл
[tilda-manager](../../skills/tilda-manager/SKILL.md).

### Что переносится и что нет

| Что | Переносится? | Как |
| --- | --- | --- |
| Блоки страницы, их порядок и содержимое, включая архивные шаблоны | да | буфер аккаунта донора |
| Скрытые блоки | да | попадают в редактор скрытыми; на публикации их нет, сверка считает только видимые |
| Свой шрифт донора | да | `donor style --apply`: ссылками на файлы донора, назначается шрифтом заголовков и текста. Не откатывается: шрифт остаётся в проекте, прежний шрифт заголовков и текста назначается в настройках сайта |
| Цвета и веса шрифтов проекта | да | `donor style --apply` через форму настроек, с записью для отката |
| Толщина и цвет подчёркивания ссылок | нет | форма настроек их не пишет; перечислены в итоге `donor style` и в докладе |
| Заголовок страницы | да | по метке карты сайта, если у приёмника заголовок «Blank page» |
| Адрес страницы | да | `donor aliases` и `donor copy --source`: адрес страницы донора; шапка, подвал и главная без адреса |
| Ссылки на домен донора и на страницы донора по ID | переписываются | `donor links`: путь на страницу копии; путь без страницы в копии остаётся с причиной |
| HTML-блоки (шаблон 131) | да, как есть | код копируется байт в байт; пустые заглушки и внешние хосты — раздел «HTML-блоки» доклада |
| Получатели заявок форм, домены, настройки страницы | нет | задаёт владелец тестового проекта |
| Zero Block | не проверено | на приёмнике с Zero Block команда отказывает `ZERO_ON_TARGET` |

### Причины отказов

| Код | Что значит | Что делать |
| --- | --- | --- |
| `TARGET_NOT_EMPTY` | на приёмнике уже есть блоки | повторить с `--replace` после «делай» или указать пустую страницу `--to` |
| `ZERO_ON_TARGET` | на приёмнике есть Zero Block | удалить его вручную или взять другую страницу |
| `PROTECTED_TARGET` | приёмник в `TILDA_PROTECTED_PAGES` | взять рабочую копию, живую страницу не трогать |
| `REPLACE_INCOMPLETE` | после удаления на приёмнике остались блоки | проверить приёмник и повторить |
| `SOURCE_EMPTY` | на странице донора нет блоков | проверить карту `donor map` |
| `DONOR_CHANGED` | состав страницы донора изменился во время переноса | остановиться, сообщить владельцу, проверить страницу донора вручную |
| `COPY_TO_BUF_FAILED`, `PASTE_FAILED` | Tilda отказала в копировании или вставке | проверить вход `session --donor` и доступ сотрудника |
| `WRITE_NOT_ALLOWED` | запись вне разрешённой страницы в сессии донора | это защита донора: искать ошибку в команде, не обходить |
| `SESSION_LOST` (код 3) | в держателе нет входа | `session --donor` для донора, `session` для тестового проекта |
| `NO_DONOR_PAGES`, `NO_SITE` | нет перечня донора или карты сайта | `donor pages`, затем `reference pages --slug demo` |
| `NO_DONOR_STYLE`, `STYLE_NOT_CONFIRMED` | нет `donor-style.json` или нет `--confirm` | `donor style --slug demo`, запись — с `--apply --confirm` после «делай» |
| `ALIAS_TAKEN` | адрес занят другой страницей тестового проекта | назвать владельцу: освободить адрес у той страницы или оставить |
| `ALIAS_INVALID`, `ALIAS_NOT_SAVED` | адрес с недопустимыми символами или Tilda не сохранила его | проверить адрес страницы донора; повторить `donor aliases` |
| `NO_PAGE_LIST` | нет перечня страниц тестового проекта | `page list` |
| расхождения `verify` после `donor links` | поле сохранилось не так, как в плане | `donor copy --replace` метки и `donor aliases`, не `rollback` |
| `SHOT_SCALED` | масштаб окна держателя искажает кадр | перезапустить держатель: при старте масштаб сбрасывается |
| порядок не совпал (`orderMatches: false`) | блоки на приёмнике не в порядке донора | повторить `donor copy --replace` |

Причины карты `donor map`: у метки нет адреса, у донора нет страницы с ролью или адресом,
адресу соответствует несколько страниц, страница пропала из слепка. Страница донора,
доступная по двум адресам, даёт в карте две метки с одним `donorPageid`: переносите её один
раз, вторую метку отметьте в сводке.

Причины `donor aliases`: роль шапки, подвала или главной, нет пары у донора, нет страницы копии,
у страницы донора нет адреса, адрес уже как у донора, адрес занят другой страницей, та же
страница донора у другой метки (дубль по второму адресу), страница защищена. Причины
`donor links`: страницы с таким путём в копии нет, поле формы. Причины пропуска меток
`donor check`: метки нет в карте, у метки нет `pageid`, та же страница донора у другой метки,
нет записи переноса, прогон остановлен после трёх сбоев подряд.

### Ложные отличия предпросмотра

`donor verify` сравнивает предпросмотр собранной страницы с опубликованным референсом. Эти
отличия — свойство предпросмотра, а не ошибка переноса:

- ссылки `tel:` в предпросмотре отдаются как `href="#"` цветом ссылок проекта;
- текст кнопки формы может переноситься на две строки против одной на публикации;
- шапка и подвал на кадре сборки — страницы `HDR` и `FTR` тестового проекта, на кадре
  референса — донорские;
- плашка «Вернуться к редактированию» на кадре сборки;
- HTML-блок показан заглушкой «Код будет выполнен на опубликованной странице»; его код и пустые
  заглушки — в разделе «HTML-блоки» доклада;
- видео-обложки и встраивания YouTube показывают другой кадр или чёрное превью;
- активный пункт меню подчёркнут только на опубликованной странице;
- процент сверки разметки ниже 100: блоки перенесены байт в байт, а предпросмотр отличается
  от публикации версией разметки.

## Правила безопасной работы

- Работайте сначала на копии страницы (`page duplicate`). ID рабочей страницы, которую
  нельзя изменять, внесите в `TILDA_PROTECTED_PAGES`. Перечень страниц с отметкой
  защищённых даёт `page list`.
- Перед каждой записью снимайте свежий `snapshot`; `verify` должен завершаться без расхождений.
- Не закрывайте браузер-держатель между командами: сессия Tilda может быть потеряна.
  Окно держателя держите свёрнутым; оно разворачивается для входа человека, а посмотреть
  в него можно командой `browser show` (свернуть обратно — `browser hide`).
- Для большой страницы соблюдайте темп чтения. `promote` по умолчанию читает пачками
  по 10, делает паузу 2,5 секунды между чтениями и 60 секунд между пачками
  (`--batch`, `--delay`, `--pause`). Не ускоряйте без отдельной проверки.
- Не публикуйте автоматически: `page publish` требует `--confirm`, но подтверждение
  должно следовать только после ручной приёмки.
- Две команды на одной странице одновременно несовместимы — держатель ставит блокировку.
- Кабинет донора только читается. Сессия донора пишет только в разрешённую страницу-приёмник
  на время вставки; остальная запись отказывает `WRITE_NOT_ALLOWED`. Каждый запуск
  `donor copy` — по явному «делай» владельца: это действие под входом чужого аккаунта.
