# Настройка

Все настройки — переменные окружения. Настройки одного сайта лежат в `.env` его **папки сайта**
(см. ниже); папка выбирается флагом `--site <папка>` или переменной `TILDA_SITE_DIR`:

```powershell
node scripts/tilda.mjs --site D:\Sites\example-site --help
```

`.env` в корне репозитория не читается: при его наличии CLI пишет предупреждение и работает дальше.
Способ задать переменные явно, без папки сайта, остался прежним — `node --env-file=<файл> scripts/tilda.mjs …`.

Шаблон — `.env.example` (только синтетические числа).

## Папка сайта

Всё, что принадлежит одному сайту, лежит в отдельной папке **вне репозитория**:

```
D:\Sites\
  example-site\          ← папка сайта (--site)
    .env                 ← TILDA_PROJECT_ID, TILDA_PROTECTED_PAGES, TILDA_CATALOG_DIR…
    site-baseline\       ← снимки, журнал, pages, project-settings, transfer
    site-reference\      ← слепки референса
    .browser-profile\    ← профиль держателя (вход в аккаунт Tilda)
    plans\               ← сгенерированные планы
  _shared\
    catalog\             ← общий каталог шаблонов (TILDA_CATALOG_DIR)
```

Создать папку и `.env`: `node scripts/tilda.mjs setup --site <папка> --project <ID>`. Команда
берёт папку только из `--site` (`TILDA_SITE_DIR` она не использует) и ID проекта только из
`--project` (одноимённую переменную окружения не использует). Существующий `.env` она не
перезаписывает:

| `TILDA_PROJECT_ID` | Что делает `setup` |
| --- | --- |
| только в `.env`, флага нет | оставляет значение файла |
| только флаг `--project` (файла нет или ключ пуст) | записывает значение флага |
| флаг и файл равны | ничего не меняет |
| флаг и файл различаются | отказ с кодом 1, файл не меняется |

Правила:

- Папка сайта обязана быть вне репозитория и содержать `.env`; иначе отказ с кодом `2`.
- Без выбранного сайта команды с данными отказывают с кодом `2` и ничего не создают.
- Путь к данным берётся так: явная переменная (`TILDA_BASELINE_DIR` и т. д.) → подпапка папки сайта → отказ.
  Корень репозитория для данных не используется; явная переменная, указывающая внутрь репозитория, — тоже отказ.
- Относительные пути в `.env` сайта (`TILDA_BASELINE_DIR`, `TILDA_REFERENCE_DIR`, `TILDA_CATALOG_DIR`,
  `TILDA_BROWSER_PROFILE`, `TILDA_DONOR_BROWSER_PROFILE`) считаются от папки сайта.
- Из `.env` сайта применяются только ключи `TILDA_*` и `LOG_LEVEL`. Остальные (например `NODE_OPTIONS`, `PATH`) не
  применяются и в держатель браузера не попадают; CLI пишет предупреждение с их именами.
- `TILDA_SITE_DIR` в `.env` сайта задавать нельзя. `--site` и `TILDA_SITE_DIR` вместе допустимы,
  только если указывают на одну папку.
- Переменная `TILDA_*`, заданная и в окружении, и в `.env` сайта с разными значениями, — отказ с именем
  переменной (значения не печатаются). Прочие переменные окружения (например `LOG_LEVEL`) главнее файла.
  `TILDA_LANG` тоже главнее файла и отказа не вызывает ([Язык сообщений](#язык-сообщений)).
- `TILDA_PROJECT_ID`, `TILDA_PROTECTED_PAGES` и `TILDA_DONOR_PROJECT_ID` выбранный сайт берёт только из своего
  `.env`: если такая переменная задана лишь в окружении оболочки (например, осталась от другого сайта),
  а в `.env` сайта её нет — отказ с кодом `2` и именем переменной. Остальные `TILDA_*` из окружения,
  которых нет в `.env` сайта (например `TILDA_DEFAULT_PAGE`), работают, но CLI пишет предупреждение с их именами.
  Отладочные `TILDA_BROWSER_DAEMON` и `TILDA_BROWSER_VISIBLE`, а также `TILDA_LANG` предупреждений не вызывают.
  `node --env-file=<файл>` вместе с `--site` для этих трёх переменных не подходит — впишите их в `.env` сайта.
- Каталог шаблонов общий для всех сайтов и задаётся только `TILDA_CATALOG_DIR`; из папки сайта он не выводится.
- Профиль браузера — это вход в один аккаунт Tilda, а не в один сайт. У каждой папки сайта свой профиль;
  сайты одного аккаунта могут указать общий профиль через `TILDA_BROWSER_PROFILE` (одновременно работать
  с ним нельзя: второй запуск ждёт замка профиля).

## Переменные `TILDA_*`

| Переменная | Обязательна | Назначение |
| --- | --- | --- |
| `TILDA_SITE_DIR` | нет | Папка сайта (то же, что `--site`). Из `.env` сайта не задаётся. |
| `TILDA_PROJECT_ID` | для онлайн-команд | Числовой ID проекта Tilda. Команда с другим `projectid` отклоняется. |
| `TILDA_PROTECTED_PAGES` | для онлайн-команд | Список ID страниц, защищённых от записи, через запятую. Переменная должна быть задана **явно**: пустое значение `TILDA_PROTECTED_PAGES=` разрешает запись во все страницы, отсутствие переменной — ошибка. |
| `TILDA_LANG` | нет | Язык сообщений CLI: `en` или `ru`. Пусто — язык системы. Подробнее — [Язык сообщений](#язык-сообщений). |
| `TILDA_DEFAULT_PAGE` | нет | Числовой ID страницы, используемой при отсутствии `--page`. Для `page publish` не подставляется — нужен явный `--page`. |
| `TILDA_CATALOG_DIR` | для команд каталога и `reference plan` | Общая для всех сайтов папка каталога шаблонов (`<tplid>.json`, `<tplid>.settings.json`). Значения по умолчанию нет. |
| `TILDA_BASELINE_DIR` | нет | Путь для снимков, инвентаря, журнала и скриншотов. По умолчанию `<папка сайта>/site-baseline`. |
| `TILDA_BROWSER_PROFILE` | нет | Путь к отдельному профилю Chrome. По умолчанию `<папка сайта>/.browser-profile`. |
| `TILDA_REFERENCE_DIR` | нет | Каталог слепков референс-сайтов (HTML, структура, картинки) для `reference fetch`. По умолчанию `<папка сайта>/site-reference`. |
| `TILDA_DONOR_PROJECT_ID` | для команд донора | Числовой ID проекта донора для `browser --donor`, `session --donor` и `donor …`. Должен отличаться от `TILDA_PROJECT_ID`. Агент находит его в слепке: атрибут `data-tilda-project-id` в разметке опубликованных страниц. |
| `TILDA_DONOR_BROWSER_PROFILE` | для команд донора, кроме `donor aliases`, `donor links`, `donor check` | Путь к профилю Chrome держателя донора, например `./.browser-profile-donor` (от папки сайта). В профиле хранится сессия аккаунта донора. Трём командам из исключения хватает `TILDA_DONOR_PROJECT_ID`: держатель донора они не открывают, а читают сохранённый перечень его страниц. Должен отличаться от профиля тестового держателя. Значения по умолчанию нет. |

Все ID — положительные целые числа; иное значение даёт `ConfigError` и код выхода 2.

## Язык сообщений

Язык справки, итогов, ошибок и отчёта `doctor` выбирается по порядку:

1. флаг `--lang en|ru`;
2. переменная `TILDA_LANG` (`en` или `ru`);
3. язык системы: локаль `ru*` даёт русский, любая другая — английский;
4. иначе — английский.

Пустое `TILDA_LANG=` считается незаданным, то есть берётся язык системы. Значение не из `en` и `ru` — отказ
с кодом `2`.

`TILDA_LANG` можно вписать в `.env` сайта, но у этого есть границы:

- `.env` сайта читается после выбора сайта. Поэтому справка (`--help`) и ошибки разбора флагов идут на языке
  флага, окружения или системы, а не файла.
- `doctor` и `setup` работают до выбора сайта и `TILDA_LANG` из `.env` сайта не читают. Для них язык
  задаётся `--lang` или переменной окружения.
- Если `TILDA_LANG` задана и в окружении, и в `.env` сайта, побеждает окружение, без отказа (для прочих `TILDA_*`
  разные значения — отказ).

Что переводится, а что нет:

- Журнал (stderr) всегда на английском, что бы ни было выбрано.
- В `--json` поле `status` — нейтральный код (например `done`), а `statusText` — перевод; у пунктов `doctor`
  есть поле `key` — ключ сообщения.
- Доклады, которые команды пишут в файлы (`reports/…`), составляются на языке запуска.
- Команды, флаги, имена переменных и файлов, коды выхода не переводятся.

Записать язык в `.env` нового сайта можно при создании:

```powershell
node scripts/tilda.mjs setup --site D:\Sites\example-site --project <ID проекта> --lang ru
```

`setup --lang` пишет `TILDA_LANG=ru` в `.env` сайта и выводит итог на этом же языке. Если в существующем `.env`
стоит другой язык, `setup` заменит его без отказа (в отличие от `TILDA_PROJECT_ID`). Без `--site` флаг только
выбирает язык вывода, ничего не записывая.

## Диагностика

`node scripts/tilda.mjs [--site <папка>] doctor` — проверка установки и папки сайта: Node.js,
зависимости, Chrome, git, `.env`, скилл. Только читает и печатает команды исправления; разбор
пунктов — в [Начале работы](getting-started.md#что-сказал-doctor).

| Переменная | Значения | Назначение |
| --- | --- | --- |
| `LOG_LEVEL` | `DEBUG`, `INFO` (по умолчанию), `WARN`, `ERROR` | Порог логов. Логи идут в stderr; stdout занят коротким итогом команды. `DEBUG` печатает тела запросов к Tilda без cookies. |
| `TILDA_BROWSER_DAEMON` | `0` | Отладка: не подключаться к держателю, а запустить свой Chrome в процессе команды (закроется вместе с ней). Сессия при этом не живёт между командами. |
| `TILDA_BROWSER_VISIBLE` | `1` | Отладка: держать окно браузера на экране вместо свёрнутого. Обычная работа идёт со свёрнутым окном. |

Сообщения-ошибки идут на языке запуска, а строки предупреждений — из журнала (stderr), поэтому они всегда
по-английски.

| Сообщение | Что делать |
| --- | --- |
| `не выбран сайт — укажите --site <папка сайта> или …` | Добавьте `--site <папка сайта>` или задайте `$env:TILDA_SITE_DIR`; либо укажите переменную пути, названную в сообщении. |
| `.env in the repository root is not read` (предупреждение) | Перенесите файл в папку сайта и запускайте с `--site <папка сайта>`. |
| `папка данных внутри репозитория продукта` | Вынесите папку сайта (или указанную переменную) за пределы репозитория. |
| `переменные заданы и в окружении, и в .env папки сайта` | Уберите названные переменные из окружения: `Remove-Item Env:TILDA_PROJECT_ID`. |
| `переменные заданы только в окружении, а в .env папки сайта их нет` | Впишите названные переменные в `.env` сайта либо уберите их из окружения: `Remove-Item Env:TILDA_PROJECT_ID`. |
| `site .env keys outside TILDA_* and LOG_LEVEL are not applied` (предупреждение) | Уберите названные ключи из `.env` сайта: инструмент их не читает. |
| `TILDA_* taken from the environment, not in the site .env` (предупреждение) | Проверьте, что значения принадлежат этому сайту; лучше перенесите их в `.env` сайта. |

## Что не попадает в Git

Данные сайта лежат в папке сайта вне репозитория: `.env`, профили держателей (в том числе профиль донора
с сессией его аккаунта), `site-baseline/`, `site-reference/`, `plans/`. Строки `.gitignore` для `.env`,
`.browser-profile*/`, `site-baseline/`, `site-reference/`, `scripts/plans/`, `node_modules/`, `*.log`
остаются страховкой. Адрес референса и ID страниц живут в папке сайта, в репозиторий они не попадают.
Копии скилла `.claude/skills/tilda-manager` и `.agents/skills/tilda-manager` ставит `setup`;
они игнорируются `.gitignore`.
Не помещайте в планы, снимки и журнал пароли, cookies или ключи API.

## Снятие защиты на один запуск

Флаг `promote --unprotect` снимает защиту живой страницы только на этот вызов; переменную
`TILDA_PROTECTED_PAGES` он не меняет. Это осознанное действие человека, а не настройка.
